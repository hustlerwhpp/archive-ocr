# Архив OCR

Веб-приложение для оцифровки рукописей и машинописного текста из архива.
Всё работает в браузере, сервера нет, бесплатно, без ключей и регистрации.
Фото и документы не покидают компьютер.

## Что умеет

- Загрузка фото (JPG, PNG, WebP) и PDF: перетаскивание, выбор файла, вставка из буфера (Ctrl+V).
- Очередь страниц, пакетное распознавание по одной странице, с паузой и кнопкой «Стоп».
- Предобработка на Canvas: градации серого, контраст, бинаризация по Отсу, апскейл до ~300 DPI, поворот.
- Распознавание через Tesseract.js v6: языки rus / eng / rus+eng, настройка PSM, один воркер на сессию, прогресс в %.
- Три режима качества для слабых ПК: экономный (до 1200 px), обычный (до 1800 px), максимальное качество (до 2400 px).
- Редактор: слева фото, справа редактируемый текст. Неуверенные слова подсвечены жёлтым и кликабельны в обе стороны: слово → рамка на фото, рамка на фото → слово в тексте. Статистика: символы, слова, уверенность, время.
- Экспорт в .txt, .docx и копирование в буфер обмена.
- Кнопка «Пример для проверки» — генерирует на Canvas страницу-образец архивной справки с известным текстом.
- Режим «Помощник транскрибации» для рукописей (см. ограничения ниже).
- Режим «Рукопись (PP-OCRv6, бета)» — локальная нейросеть для русского рукописного текста (см. ниже).
- Кнопка «Распознать заново» для выбранной страницы; «Распознать всё» повторно распознаёт страницы, распознанные другим движком.
- Бенчмарк для подбора быстрого режима под конкретный компьютер (см. ниже).

## Как запустить локально

Просто откройте `index.html` в браузере. Интернет нужен только при первом запуске:
движок Tesseract.js и языковые данные скачиваются с CDN (~10–15 МБ) и кэшируются браузером,
дальше приложение работает офлайн.

Если браузер блокирует `file://` для модулей — запустите локальный сервер одной командой:

```bash
npx serve .
# или
python3 -m http.server 8000
```

и откройте http://localhost:8000 (или адрес, который покажет `serve`).

## Как включить GitHub Pages

1. Загрузите папку в репозиторий (например, `hustlerwhpp/archive-ocr`).
2. В репозитории: Settings → Pages → Source: Deploy from a branch → Branch: `main`, папка `/ (root)` → Save.
3. Через минуту сайт будет доступен по адресу `https://hustlerwhpp.github.io/archive-ocr/`.

Сборки нет — это статичный сайт: `index.html`, `app.js`, `styles.css` плюс файлы
PWA (`manifest.webmanifest`, `sw.js`, `icon-192.png`, `icon-512.png`, `icon-512-maskable.png`).

## PWA (установка и офлайн)

Приложение — PWA (Progressive Web App), его можно установить как отдельное
приложение на компьютер или телефон:

- **Chrome/Edge (Windows, Android):** в шапке сайта появляется кнопка
  «Установить приложение» (событие `beforeinstallprompt`). После установки
  приложение открывается в отдельном окне, без адресной строки браузера.
- **iPhone/iPad:** кнопки установки нет (так устроен iOS) — в шапке показывается
  подсказка: «Поделиться» → «На экран “Домой”».
- **Офлайн:** после первого запуска оболочка приложения и CDN-библиотеки
  (Tesseract.js, onnxruntime-web + WASM, pdf.js, docx) кэшируются service worker
  (`sw.js`, кэш `archive-ocr-v1`, cache-first). Модели в Cache Storage НЕ кладутся —
  они уже кэшируются в IndexedDB (база `archive-ocr-models`), повторный визит
  без скачивания. Для `index.html` — network-first с fallback в кэш.
- **Обновление:** при публикации новой версии в шапке появляется
  «Доступна новая версия приложения — Обновить». Кнопка активирует новый
  service worker и перезагружает страницу. Старые кэши чистятся автоматически.
- **Локальный файл:** при открытии как `file://` service worker не регистрируется
  (браузеры это запрещают) — приложение просто работает как обычный сайт.
  Для проверки PWA запустите локальный сервер (`python3 -m http.server 8000`)
  или откройте сайт на GitHub Pages.

## Лимит памяти

Настройка «Лимит памяти (нейросети)» в панели настроек: ползунок 1–8 ГБ
с шагом 1 ГБ, значение сохраняется в localStorage, по умолчанию 2 ГБ.
Лимит действует для режима «Рукопись»; Tesseract для печати использует
~10–15 МБ независимо от лимита. Рядом с ползунком всегда видно, что выбрано:
модель, размер скачивания при первом запуске и примерная RAM вкладки.
При снижении лимита сессии старого движка выгружаются из памяти
(перезагрузка моделей при следующем распознавании — из кэша IndexedDB,
без повторного скачивания).

| Лимит | Модель | Скачивание | RAM вкладки | Статус |
|---|---|---|---|---|
| 1 ГБ | PP-OCRv6 Tiny det + Tiny rec | ~4 МБ + ~14 МБ рантайм | ~0,3–0,5 ГБ | Готов. Замерено на курсиве после исправлений 2026-11-11: авто-детекция 54%, по строкам 62%, ~1–1,4 сек/стр. |
| 2 ГБ | PP-OCRv6 Small det + Medium rec | ~72 МБ + ~14 МБ рантайм | ~1–1,5 ГБ | Готов. Честно: на курсиве Medium замеренно хуже Tiny (27% против 54%); Medium лучше для аккуратного почерка и печатного текста. |
| 3 ГБ | TrOCR q4f16 | ~294 МБ | ~0,7–1 ГБ | **Скоро — не подключён.** |
| 4 ГБ | TrOCR int8 (рекомендуемый максимум) | ~388 МБ | ~1–1,5 ГБ | **Скоро — не подключён.** |
| 5 ГБ | TrOCR int8 + beam search | ~388 МБ | ~2 ГБ | **Скоро — не подключён.** |
| 6 ГБ | TrOCR fp16 | ~770 МБ | ~2–3 ГБ | **Скоро — не подключён.** |
| 7 ГБ | TrOCR fp32 | ~1,5 ГБ | ~3,5–4,5 ГБ | **Скоро — не подключён.** |
| 8 ГБ | TrOCR fp32 + запас | ~1,5 ГБ | ~4–5 ГБ | **Скоро — не подключён.** |

Почему TrOCR «скоро»: для запуска в браузере декодер TrOCR нужно переконвертировать
в merged-формат с KV-кэшем (в репозитории `Mievst/trocr-base-handwritten-ru-ONNX`
такого файла нет). Ручной путь без кэша даёт 5–20 мин/страницу и не годится.
Выбор лимита 3–8 ГБ доступен в интерфейсе, но распознавание в режиме «Рукопись»
на этих уровнях честно отказывается с понятным текстом, а не падает:
«Режим … ещё не подключён: для TrOCR нужна переконвертация декодера…».
Точность «Эконом (Tiny)» при лимите 1 ГБ — единственная доступная; «Точный (Medium)»
включается при лимите от 2 ГБ. Для fp32 есть дополнительный риск: вкладка может
упереться в лимит кучи WASM ~4 ГБ и упасть — это тоже честно написано в интерфейсе.

## Бенчмарк

Секция «Бенчмарк» в приложении:

- **Экспресс-тест (~2 сек)** — 5 замеров предобработки на разных размерах. Работает полностью офлайн, без движка OCR.
- **Полный бенчмарк** — 3 последовательных прогона на образце справки: экономный 1200 px с бинаризацией, обычный 1800 px с бинаризацией, без бинаризации. Замеряются время, точность по известному тексту образца и уверенность движка. Прогоны идут по одному, с паузами и кнопкой остановки, чтобы не перегружать слабый ПК.
- В конце — авто-рекомендация самого быстрого режима без заметной потери точности и кнопка «Применить».

Если движок недоступен (например, заблокирован CDN), полный бенчмарк покажет понятную ошибку и предложит экспресс-тест.

## Режим «Рукопись» (PP-OCRv6, бета)

Для рукописного текста есть отдельный движок — переключатель «Движок распознавания»
в настройках: «Печать (Tesseract)» (по умолчанию) / «Рукопись (PP-OCRv6, бета)».

Как это работает:

- Детекция строк — PP-OCRv6 tiny det (PaddlePaddle, ~1,7 МБ), либо быстрый вариант
  «По строкам»: бинаризация Отсу + горизонтальный проекционный профиль (без нейросети).
- Распознавание строк — PP-OCRv6 tiny rec Cyrillic (Metrika Labs, ~2,4 МБ)
  или, по выбору, medium rec (~60 МБ). Выход модели — вероятности CTC
  (0 = blank, 1..850 = словарь, 851 = пробел).
- Рантайм — onnxruntime-web 1.31.1 с jsDelivr, один поток WASM (на GitHub Pages
  нет COOP/COEP, многопоточность недоступна). Скрипт рантайма и модели грузятся
  лениво — только при первом распознавании в режиме «Рукопись».
- Модели скачиваются с HuggingFace и кэшируются в IndexedDB (база `archive-ocr-models`),
  повторный визит — без скачивания, дальше работает офлайн. В репозитории файлов
  моделей нет.
- Предобработка для рукописей — цветной кадр без бинаризации по Отсу (синие чернила
  и курсив от неё страдают); настройки контраста и поворота из UI учитываются.
- Подсветка и клики слово↔фото работают на уровне строк: неуверенная строка
  подсвечивается жёлтым, клик по ней показывает рамку на фото.

### Честные результаты замеров (Node-тест, onnxruntime-web 1.31.1, WASM 1 поток)

Тестовая страница — рукописный курсив синими чернилами, 11 строк, эталон —
ручная расшифровка. Точность — по Левенштейну, как в бенчмарке приложения.

| Режим | Точность | Уверенность | Время |
|---|---|---|---|
| Tesseract (было) | ~0% (мусор, уверенность 17%) | 17% | 0,7 сек |
| PP-OCRv6 Tiny + авто-детекция | 54% | 63% | 1,4 сек |
| PP-OCRv6 Tiny + детекция по строкам | 62% | 69% | 1,0 сек |
| PP-OCRv6 Medium + авто-детекция | 27% | 50% | 20,3 сек |

### Исправления 2026-11-11 — баги, найденные живым тестом на archive.whpp.site

**Баг 1 — авто-детекция падала с ошибкой ONNX Runtime.** В живом браузере режим
«Рукопись» + «Авто (нейросеть)» воспроизводимо падал: `failed to call OrtRun() …
Shape mismatch attempting to re-use buffer. {1,64,60,43} != {1,64,60,44}`.
Причина найдена зондом на той же версии onnxruntime-web 1.31.1: детектор DBNet
требует, чтобы стороны входа были кратны 32, а браузер подавал ему фото как есть
(828×560). Внутри модели карты признаков ветвей FPN расходятся на 1 px
(на 828×560: `{1,64,35,52} != {1,64,36,52}`; на странице-образце 677×960 —
ровно та же ошибка `{1,64,60,43} != {1,64,60,44}`, что и в живом тесте).
Сессии тут ни при чём: распознаватель строк с разными ширинами на одной сессии
работает нормально (проверено ширинами 160/320/640 и 172/176). Исправление:
новая функция `resizeCanvasForDet()` в `app.js` — det-вход всегда округляется
к ближайшему кратному 32 (828×560 → 832×576, 1200×1700 → 672×960). После
исправления авто-детекция проходит без ошибки: 54% точности (было — падение).

**Баг 2 — «По строкам» в браузере давал ~10% против 47% в Node-тесте.**
Причина — две, обе в подготовке кропа строки для распознавателя, а не в детекции
(боксы строк в обоих пайплайнах одинаковые, контраст 1.2 и серый для профиля
проверены по отдельности — не влияют):
1. `drawImage` по умолчанию — билинейный ресемпл, он размывает тонкие штрихи
   курсива: 39% точности / 56% уверенности против 45% / 71% у Lanczos при том же
   cap 640. Исправление: `imageSmoothingQuality = 'high'` на канвасе строки.
2. Лимит ширины входа распознавателя был 640: число шагов CTC T = rw/8 = 80,
   и длинные строки обрезались (~25 символов на строку). Поднятие лимита
   до 960 (T = 120) даёт 59% точности даже с билинейным ресемплом;
   cap 1280 — 65%, но заметно медленнее, поэтому выбран 960.
   Итог после исправлений: «По строкам» — 62% / 69% (было 39% / 56% в браузере),
   «Авто» — 54% / 63%. Замеры — Node-харнесс с onnxruntime-web WASM на том же
   фото; `imageSmoothingQuality` в Node не проверить, поэтому живой тест
   на сайте после деплоя всё равно нужен.

**Баг 3 — чекбоксы «Бинаризация по Отсу» и «Градации серого» оторваны от подписей.**
Причина в CSS: `.settings-grid label { display: grid }` (специфичность 0,1,1)
перебивало `.check { display: flex }` (0,1,0). Исправление: правило
`.settings-grid label.check { display: flex }` в `styles.css`.
Попутно выяснено, почему режим качества «переключался сам» с «Экономного» на
«Обычный»: настройки не сохранялись, и любая перезагрузка страницы (в т.ч.
автоматическая при обновлении service worker) сбрасывала их на значения
по умолчанию из HTML. Исправление: настройки распознавания (качество, бинаризация,
серый, контраст, поворот, движок, детекция, точность) сохраняются в localStorage
(ключ `archiveOcrSettings`) и восстанавливаются при запуске.

Выводы, которые из этого следуют:

- Tiny заметно лучше Tesseract на рукописях, но курсив всё равно читает с ошибками:
  отдельные слова узнаваемы («Золото звенит кандалами», «Единственное оконце, затянутое»),
  но в каждой строке есть неверные буквы. Это черновик для ручной правки, а не готовая оцифровка.
- Детекция по строкам (проекционный профиль) на ровной странице работает
  даже лучше нейросетевой (62% против 54% после исправлений 2026-11-11)
  и в разы быстрее, но на плотном курсиве строки могут слипаться.
- Medium на этом тесте НЕ помог: медленнее в ~10 раз и точнее не стал (часть строк
  вообще пустые). На аккуратном печатном почерке он может быть лучше, но для курсива
  выбирайте Tiny.
- Точность 54–62% — это не провал теста, а честный уровень модели на связном курсиве.
  Производитель моделей тоже предупреждает, что курсив читается с ошибками.

## Ограничения по рукописям — честно

Tesseract обучен в основном на печатном тексте. Рукописный текст, особенно курсив,
старая орфография (ѣ, і, ъ) и неразборчивый почерк, он читает плохо — с большим числом ошибок.

Поэтому рукописи в приложении оформлены как **помощник транскрибации**: движок даёт черновик,
а человек сверяет его с фото построчно и правит вручную. Автоматическая оцифровка рукописей
здесь НЕ обещается.
